## New findings

### A. `map_lb()`: reference ranges are scaled by a factor the result may not have used

`R/map-lb.R:70–92`. `.factor` is the *local* conversion factor — `CONV_FACTOR`
when the collected unit matches `CONV_FROM`, otherwise `1`. `LBSTRESN`,
however, prefers the EDC's own converted value:

```
LBSTRESN = if_else(!is.na(.rave_n), .rave_n, round(.orres_n * .factor, 4))
LBSTNRLO = round(LBORNRLO * .factor, 4)
```

When the EDC supplies `RAVE_STD` **and** the collected unit is not
`CONV_FROM`, `.conv` is `FALSE`, so `.factor` is `1` — the result is in
standard units and the ranges stay in collected units. The comment two lines
above ("same factor as the result, so the comparison below is done entirely in
standard units") is only true on the local-factor path.

Concrete failure: glucose collected as `5.0 mmol/L` with `GLUC_STD = 5.0`,
`GLUC_STD_UN` blank, ranges `70`/`100` (mg/dL, as the site's lab reports
them). `.conv` is `FALSE`, `LBSTRESN = 5.0`, `LBSTRESU = "mmol/L"` (via the
new `CONV_TO` arm, which fires on `!is.na(.rave_n)`), `LBSTNRLO/HI = 70/100`.
`LBNRIND` = `"LOW"` for a perfectly normal glucose — and it flows straight
into ADLB as `ANRIND`, `BNRIND`, and every shift table built on them. The
validator's `adlb-range-not-from-lb` check compares ADLB against the SDTM
record, so both agree and neither complains.

This predates v0.3.0, but the new `LBSTRESU` logic makes it reachable in a way
it wasn't: previously the mislabelled unit at least matched the mislabelled
ranges. Now the unit follows the conversion actually applied and the ranges
don't.

The fix is to derive the range scaling from the ratio actually applied to the
result rather than from `.factor` — or, where the EDC supplied the standard
value, to require the EDC's standard ranges too and leave `LBSTNRLO/HI` missing
when it didn't (`LBNRIND` already handles missing bounds correctly). Either
way, `.conv` is now the variable that knows the answer; the range lines should
be reading it.

Related, smaller: an analyte with **no** `spec$units` row but a populated
`RAVE_STD` and blank `RAVE_STDU` gets `LBSTRESN` from the EDC and
`LBSTRESU = LBORRESU` (the *collected* unit) — the same class of mislabel in
the other direction. And the `CONV_TO` arm firing on `!is.na(.rave_n)` assumes
the EDC's standard unit equals the spec's `conv_to`. That assumption is
defensible; it deserves the same visibility treatment the new
`lb-unit-unmapped` WARN got — a WARN when `RAVE_STD` is populated and
`RAVE_STDU` is blank.

### C. Four `validate_adam()` checks are not NA-safe, and their twins are

The file uses two comparison idioms. The careful one, e.g. ADLB's
`adlb-ady-wrong` (`R/validate-adam.R:665–669`):

```
filter(xor(is.na(ADY), is.na(.expect)) |
         (!is.na(ADY) & !is.na(.expect) & ADY != .expect))
```

and the bare one, in four places:

- `trtdurd-wrong` (:119) — `TRTDURD != .rule_trtdurd(...)`
- `trtemfl-not-derivable` (:306) — `filter(TRTEMFL != .expect)`
- `astdy-wrong-anchor` (:329) — `filter(ASTDY != .expect)`
- `advs-ady-wrong` (:511–514) — `filter(ADY != .expect)`

In each, an `NA` in the *built* column makes the comparison `NA` and
`filter()` drops the row. `.rule_trtemfl()` never returns `NA`, so an `NA`
`TRTEMFL` in a built ADAE is precisely the corruption that check exists to
catch — and it passes. `advs-ady-wrong` is the sharpest case because its ADLB
twin twenty lines later is written correctly; the asymmetry looks accidental
rather than argued.

Worth adding a test in the same shape as the existing "a flipped TRTEMFL is
recomputed and flagged", but blanking the value instead of flipping it.

### D. `new_study_spec(derivations = )` validates against functions it then discards

`R/spec.R:75–120`. The argument is used for the `unknown_der` check and never
stored on the spec. Nothing downstream can supply it either: no mapper calls
`map_variables(derivations = )` — the parameter has no caller in `R/`.

The consequence is a spec that passes construction and fails at build.
`test-spec.R` demonstrates it: a spec declaring `dmdy_local` gets
`expect_s3_class(..., "study_spec")`, and `build_all()` on that spec would die
in `map_variables()` with `unknown derivation 'dmdy_local'`. That inverts the
intent of finding 12 — the whole point was "fail here, not halfway through a
build."

Storing the list on the spec (`spec$derivations`) and having the mappers pass
`spec$derivations` through would close it, and would give the map-time
extension mechanism an actual wiring rather than a documented one.

### E. The derivation contract is documented but not checkable

`R/derivations.R:6–13` states the contract — a collected source is read through
`row$crf_field`, never a literal name — and `usubjid`, `country`, `dsdecod`
and the six `*_ongoing` entries now depend on it. A spec row that omits
`crf_field` for one of those fails at build time with
`subscript out of bounds`, which is the failure mode finding 12 was meant to
eliminate.

Since the registry now knows which entries need a field, that is declarable:
a `needs_field` attribute on the registry (or a parallel character vector of
entry names), checked in `new_study_spec()` against
`is.na(variables$crf_field)`. About six lines, and it makes the contract
enforced rather than advisory.

### F. `LBNRIND` is a third implementation of the ANRIND rule

`R/map-lb.R:93–98` is structurally `.rule_anrind()` — value plus both bounds,
`LOW`/`HIGH`/`NORMAL`, same NA handling. `derive_adlb()` copies `LBNRIND`
straight into `ANRIND`, and `validate_adam()` recomputes `ANRIND` with
`.rule_anrind()`. So the two agree today by coincidence of authorship, and a
future edit to one surfaces as an `adlb-anrind-wrong` ERROR — loud, but
attributed to the wrong layer.

The SDTM-vs-ADaM layering argument for keeping them separate is real, and the
counter-argument is that `adam-rules.R` exists specifically because "two copies
that agree today" is what produced findings 1, 2 and 15. If they stay separate,
a comment at `map-lb.R:93` naming `.rule_anrind()` as the deliberate twin
would at least make the next reader check both.

### G. `build_define_xml()`'s XPath failure mode is still silent

`R/define-xml.R:262–265`. The typo is fixed and the test now counts
`ValueListRef`, but the underlying hazard is unchanged: `xml_find_first()`
returning `xml_missing` still makes `xml_add_child()` a no-op. The test pins
this only for `spec_synth01`'s two value lists; a study whose `spec$bds` or
`spec$tests` name a variable absent from the `ItemGroupDef` reintroduces the
orphan silently.

A guard — `if (inherits(parent_ref, "xml_missing")) stop(...)` naming the OID
it couldn't find — converts a class of silent metadata loss into a build
failure for one line.

### H. `generate_rave_extract()` still leaves an RNG trace when there was none

`R/generate-rave-extract.R:1271–1282`. `rng_hold` is `NULL` when
`.Random.seed` didn't exist, the `on.exit` does nothing, and `set.seed()`
inside has created one. A caller in a fresh session goes from "no seed" to
"seeded" — the same contract violation, one step smaller. Restoring the absent
case means removing `.Random.seed` from `globalenv()` on exit. The edge-case
test covers only the exists branch.

### I. Trailing comma

`R/adam-adae.R:90`: `TRTEMFL = .rule_trtemfl(ASTDT, TRTSDT, TRTEDT),` before
the closing paren. Legal — `rlang::enquos()` ignores trailing empty arguments —
and lintr's defaults don't catch it. Cosmetic.

## Standing note on the test strategy

The v0.3.0 additions fix the structural blind spot the last review named: the
seeded generator can't produce these inputs, so `test-edge-cases.R` and
`test-adam-rules.R` build them by hand. Finding A is the one place where that
discipline hasn't been applied yet — an LB record with an EDC-supplied standard
value and a collected unit that isn't `CONV_FROM`. Adding that fixture would
have surfaced it.
